Um card, duas voltas

A pauta, o ensaio e o cliente parecem três coisas que precisam ficar se atualizando. Não são. São três leituras do mesmo objeto — e é por isso que o modelo se sustenta.

Decidido pelo founderImplementado no protótipo Pendente na API — ver o fim

Onde o card nasce

Na pauta, não no ensaio.

O card nasce no calendário, em rascunho. O calendário é o Plan — é onde o trabalho é planejado antes de existir. Ele aparece no quadro do Ensaio quando alguém começa, ou seja, quando sai de rascunho.

Essa parte é deliberada: setenta cards de um cliente parados numa coluna seriam um paredão, não um quadro. O quadro mostra o que está em movimento.

Não há três lados. Há um campo.

O estado do card mora em um único campo, chamado fase. A coluna do Ensaio não é um segundo campo guardando a mesma coisa — ela é uma leitura da fase. Arrastar no quadro escreve a fase. A decisão do cliente escreve a mesma fase. O calendário lê a mesma fase.

Ninguém sincroniza nada porque nada é copiado. Não existe "atualizar o outro lado": o outro lado é o mesmo dado.

O card dá duas voltas

Não é uma esteira que anda para a frente uma vez só. É um ciclo que roda duas vezes no mesmo card: a primeira volta aprova o texto, a segunda aprova a peça. É o que PDCA sempre foi.

A TRAVA

A regra virou desenho, não aviso. A coluna "Com o cliente" não aceita ser movida por ninguém da agência. Não há como burlar por distração.

A DEVOLUÇÃO

Pedido de alteração não cria card. Devolve este para Do, em vermelho, com as palavras do cliente coladas nele.

O AVISO

Uma notificação por lote, nunca uma por card. Cinco avisos separados treinam o cliente a ignorar todos.

O que acontece quando o cliente pede mudança

Este é o caminho que costuma se perder nas ferramentas: o pedido chega, alguém lê, e ele morre num aviso. Aqui ele vira trabalho.

  1. O cliente escreve o que quer mudar e decide. Só isso move o card para fora da coluna dele.
  2. O card volta para Do — criado se era texto, producao se era peça. É o mesmo card, não um novo.
  3. As palavras do cliente ficam coladas no card, com autor e data, no registro de alterações. Não viram mensagem solta.
  4. Abre uma tarefa no Ensaio, ligada a esse card. O pedido entra na fila de quem produz, com nome e dono.
  5. A agência refaz e envia de novo. O card recomeça a volta em que estava — não volta ao começo de tudo.

Onde isso ainda não está de pé

Tudo acima está decidido e funcionando no protótipo. Na API, não — e a razão é específica o bastante para valer uma decisão antes de escrever código.

O problema, em uma frase

A API tem um AWAITING_APPROVAL só. Ela não consegue distinguir "com o cliente pelo texto" de "com o cliente pela peça".

Os três caminhos

A · recomendado

A fase substitui o status

Um enum com as onze fases, no lugar do ContentStatus. Um campo, uma verdade — nenhuma divergência é possível porque não há o que divergir.

B

Status mais um campo de volta

Barato de escrever e reintroduz exatamente o defeito que a decisão do card único matou: dois campos dizendo parte da mesma coisa, podendo discordar.

C

Deixar como está e traduzir na borda

Empurra a ambiguidade para cada consumidor. O primeiro cliente de API de terceiro herda o problema sem o mapa.

O custo de A é uma migração de enum feita uma vez, contra uma classe de bug que voltaria para sempre. E ela cabe agora, porque os blocos que escrevem conteúdo ainda não foram implementados — depois deles, sai caro.

Nada disso mexe no lote. O card é a unidade que é escrita, enviada, decidida e volta; o lote continua sendo como um conjunto de cards vai ao cliente de uma vez, com selo e termo. São coisas diferentes e as duas existem.
